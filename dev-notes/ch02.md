# 第二章开发记录

## Brainstorm 设计定稿（2026-09-23）

- 用户关键原话："我要用 Superpowers 模式给现有的客服系统装上查数据的能力"；"工具链要长在客服聊天本身"；"只做单轮调用"；"代码简洁易懂"。
- 关键产出：完成 Function Calling 架构设计，选择独立聊天编排服务与工具注册/执行层；spec 写入 `docs/superpowers/specs/2026-09-23-ch02-function-calling-design.md`。
- 用户确认：采用路径 2；无需用户提供 DDL，使用 SQLAlchemy ORM 定义四表；聊天页按 Vibe Coding 方式实现。聊天请求的 `user_id` 可选，无认证时缺省演示用户 ID。
- 技术资料：按要求用 Context7 查阅 FastAPI SSE、SQLAlchemy 2.0 ORM/session transaction、LangChain `@tool`/`bind_tools`/`ToolMessage` 最新文档。
- 用户纠偏与决定：FAQ 用参数化 `LIKE` 查询且“邮费是多少”漏召回作为预期样例记录；Function Calling 严格单工具、无自动 Agent loop；三个外部业务数据工具仅随机生成演示数据。
- 翻车与返工：初次没跟随 `/root/.agents/skills/superpowers` 符号链接而误判技能未挂载，已重新读取要求的工作流技能。自检发现第一章没有 `user_id`，补充演示默认值；并明确工具选择阶段缓存内容片段，确定响应类型后才发 SSE，避免工具轮展示未确认文本。
- 下一阶段：等待用户审阅 spec；获批后编写实施计划，再等待用户确认执行方式。
